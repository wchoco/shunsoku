# コマンドラインからのキャプチャは別の exe にし、常駐本体に名前付きパイプで依頼する

コマンドラインからのキャプチャは、常駐本体の `shunsoku.exe`（GUI サブシステム）とは別のコンソールサブシステムの `shunsoku-cli.exe` で受け付ける。CLI は自分では撮らず、常駐本体に名前付きパイプで依頼して、結果（保存したパス、エラー）を受け取ってから終了コードを返す。常駐本体が動いていなければ CLI が起動してから依頼し、本体はそのまま常駐を続ける。依頼の最初にプロトコルのバージョンを照合し、合わなければ断る（互換性は保たない）。2 つの exe は同じ zip に入れて配る。

詳細な仕様は [コマンドラインからのキャプチャ実行](https://github.com/wchoco/shunsoku/issues/16) の解決コメントにある。

## Considered Options

- **`shunsoku.exe` 1 つにまとめ、`AttachConsole(ATTACH_PARENT_PROCESS)` で親のコンソールに書く**: cmd や PowerShell は GUI サブシステムの exe の終了を待たないので、プロンプトが先に戻り、出力が後から混ざり、終了コードも取れない。スクリプトから使えない。
- **常駐本体に頼らず、CLI が単独で撮って終わる**: スクラップを出せない（スクラップは常駐本体が持つ）。キャプチャと保存の処理が常駐側と CLI 側に分かれ、定型領域の設定の解釈やファイル名テンプレートが 2 か所で動く。
- **別の exe にして、常駐本体に依頼する（採用）**: 処理の経路は常駐側の 1 本で済み、CLI は引数の解釈と依頼・応答の受け渡しだけを持つ。

## Consequences

- 常駐本体は、外から依頼を受け付ける口（名前付きパイプのサーバ）を持つ。パイプは現在のユーザーとセッションだけが開けるようにする。
- M1 の時点では口を作らないが、ホットキーやトレイメニューからのキャプチャと同じ入口に、外からの依頼を後から足せる構造にしておく。実装は M3。
- CLI の引数の解釈、依頼と応答の形式、終了コードへの対応付けは Win32 に触れないロジックとしてテストの境目に置ける。
