# 範囲選択の画面は、撮った画像を GPU に置いたままモニタごとに表示する

範囲選択キャプチャのホットキーを押したら、Desktop Duplication でモニタごとの画面を**並列に**取得し、その画像を CPU に書き戻さず GPU 上のテクスチャに置いたまま、**モニタごとに 1 枚ずつ**作る最前面ウィンドウへ flip-model のスワップチェーン（D3D11、`DXGI_SWAP_EFFECT_FLIP_DISCARD`）で表示する。CPU への書き戻しは、ユーザーが選んだ範囲を切り抜くときにその範囲だけ行う。範囲選択の画面を閉じたらテクスチャとスワップチェーンを解放し、`IDXGIDevice3::Trim` で常駐時のメモリを戻す。

[MVP の範囲とフェーズ分け](https://github.com/wchoco/shunsoku/issues/9) で性能の目標値はリリース条件にしないと決めたが、この方式は範囲選択の画面とキャプチャの層の作りそのものを決めるため、後から変えにくい。

## Considered Options

計測環境は Windows 11、Intel Iris Xe、4K 150% が 2 枚と FHD 100% が 1 枚。ホットキーの入力から DWM への反映（`DwmFlush`）までの 20 回の中央値:

- **全画面を CPU に書き戻し、仮想スクリーン全体を覆う 1 枚のウィンドウに GDI で描く（ADR-0001 の時点の方式）**: 136ms。約 74MB の書き戻しと 100MB の GDI 描画が支配的で、取得を並列にしても縮まない（140ms）。
- **GPU に置いたまま、仮想スクリーン全体で 1 枚のウィンドウ**: 126ms で、ばらつきが大きい（最小 59ms / p90 143ms）。DPI の異なるモニタにまたがる巨大なスワップチェーンになる。
- **GPU に置いたまま、モニタごとのウィンドウ（採用）**: 103ms（p90 116ms）。撮影 10 回後の Private Working Set は 20.6MB（現行は 15.8MB）。700×500 の切り抜きの書き戻しは約 2ms。
- **Desktop Duplication を常駐中も開いたままにする**: ADR-0001 の計測で 94ms だが、直前の画像を持ち続けるため常駐時メモリが 87MB になり、30MB の目標を大きく超える。

## Consequences

- 範囲選択の画面の描画（固定画像、選択枠、拡大鏡や座標表示などの UX）は D3D11 の上で組む。GDI では描かない。スクラップは従来どおり layered window（`UpdateLayeredWindow`）で、この決定の対象外。
- 選択範囲はモニタをまたげるので、ドラッグの状態はスクリーン座標（物理ピクセル）で持ち、各モニタのウィンドウがそれぞれ自分の範囲を描く。切り抜きは選択範囲と重なるモニタのテクスチャから集めて 1 枚にする。
- HDR のモニタでは Desktop Duplication の画像が 8bit BGRA ではないので、[キャプチャで撮れない・特殊なケースの扱い](https://github.com/wchoco/shunsoku/issues/12) で決めた SDR への変換（モニタごとの SDR 白基準で 8bit sRGB に）を、表示する前に GPU 上で行う必要がある。範囲選択の画面とスクラップは同じ変換後の画像を使う。
- 残る時間の内訳は、Duplication を開いた直後の空フレームの次を待つ 25〜35ms、3 枚のウィンドウの表示に約 21ms、DWM の反映に約 22ms。ウィンドウの事前生成などで縮める余地はあるが、性能値はリリース条件ではないので実装時の改善として扱う。
- 計測プロトタイプは捨てブランチ `prototype/14-overlay-latency` の `prototypes/overlay-bench` にある（マージしない）。
